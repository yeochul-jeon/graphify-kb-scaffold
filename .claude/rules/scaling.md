# 스케일링 가이드

## 세는 단위

**아티클 = `wiki/concepts/*.md` + `wiki/topics/*.md`.** `raw/` 와 `output/` 은 세지 않는다 — 전자는 원천 아카이브고 후자는 산출물이라 탐색 전략의 대상이 아니다.

## 현재 구간 — 중규모 (2026-08-16 측정)

| 항목 | 값 | 출처 |
|---|---|---|
| `wiki/concepts` | 314 | `ls wiki/concepts/*.md \| wc -l` |
| `wiki/topics` | 6 | `ls wiki/topics/*.md \| wc -l` |
| **합계** | **320** | 중규모(100~500) 구간 |

> 참고: `raw/**/*.md` 는 357건이다(같은 날). 어느 단위로 세도 중규모라 단위 모호성으로 구간이 갈리지 않는다.
>
> 🔴 **이 표를 다른 문서로 복제하지 않는다.** 복제본이 낡아 원본과 갈린 실례가 있다(`docs/architecture.md` 구간표, 2026-08-15 검토에서 발견 후 역참조로 대체).

## 소규모 (~100 아티클)

- `wiki/index.md`를 항상 먼저 읽어 관련 개념 파악
- 관련 wiki 파일만 선택적으로 읽기 (전체 스캔 금지)
- Grep으로 키워드 검색 후 좁혀가기

## 중규모 (~100~500 아티클) — 현재 구간

컨텍스트 제한 도달 시 적용:

1. **graphify query 우선**: `CLAUDE.md` 가 개념 질의의 첫 행동으로 강제하는 경로다. 반환된 `source_file` 로 후보를 좁힌 뒤에 파일을 연다
2. **index.md 기반 필터링 강화**: 태그로 후보 좁히기 → 최대 10개 파일만 읽기
3. **Grep 적극 활용**: `Grep(pattern, path="wiki/")` 키워드 사전 필터링

## 대규모 (~500+ 아티클)

벡터 DB 없이 한계에 도달하는 시점. 대응 방안:

- wiki/ 전체를 읽지 않고 **graphify query + index.md + backlinks.md + Grep** 만으로 답변 시도
- 답변 품질이 낮다고 판단되면 "관련 wiki 파일 수가 많아 일부만 참조했습니다" 명시

> ⚠️ **이 절은 한때 `/synthesize` (합성 데이터 생성) 도입을 권고했으나 그 명령은 구현된 적이 없다** — `.claude/commands/`·`scripts/` 어디에도 없다(2026-08-15 검토 확인). 출처는 `docs/improvement-plan.md` §3.4 의 **제안**(2026-04-07, 전제조건 "20+ verified 페이지")이며, 규칙 문서가 그 제안을 확정된 대응책처럼 옮겨 적은 것이 문제였다. **미구현 명령을 대응책으로 전파하지 않는다.** 이 구간의 실제 대응책은 위 두 줄이며, 그 이상이 필요해지면 그때 사람이 결정한다.

## 핵심 원칙

- **읽기 순서**: `graphify query` → 반환된 핵심 파일 (필요 시 `index.md` 태그 프리페이스) → 해당 `concepts/` (never 전체 `wiki/`)
  - ⚠️ **`topics/` 를 경유하도록 지시하지 않는다** (2026-08-16 정정). 실제 탐색 경로가 그렇지 않기 때문이다 — `CLAUDE.md` 첫 행동 규칙도 `wiki/index.md` 태그 탐색("해당 concepts/ 파일만 읽기")도 `topics/` 를 거치지 않는다. `wiki/topics/` 6건은 유지·갱신하되 라우팅 계층으로 규정하지 않는다.
- **컨텍스트 절약**: 답변에 불필요한 파일은 읽지 않는다
- **명시**: 컨텍스트 제한으로 일부 wiki 파일을 읽지 못했다면 사용자에게 고지
